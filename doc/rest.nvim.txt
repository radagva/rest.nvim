1. INTRODUCTION					*rest.nvim-introduction*

rest.nvim is a REST client for Neovim. It parses `.http` files (request
line, headers and body per RFC 9112), runs the request under the cursor
with curl, and shows the response in a split.

Requires Neovim 0.12+ and curl. jq is optional and only used to
pretty-print and filter JSON output.

Installation, the `.http` format, request chaining and the full feature
tour live in the README: https://github.com/radagva/rest.nvim

==============================================================================
2. COMMANDS						*rest.nvim-commands*

								*:RestRun*
:RestRun	Execute the .http request under the cursor and show the
		response. The request is resolved against file-level
		`@definitions`, the active environment and previous
		responses (in that order of precedence).

								*:RestList*
:RestList	Pick a request from all .http files under `list.dirs` and
		jump to it. See the `list.picker` option for backends.

							*:RestCopyCurl*
:RestCopyCurl	Copy the request under the cursor (variables resolved) as
		a curl command to the system clipboard (`+`), ready to paste
		into a terminal, and to the unnamed register.

							*:RestImportCurl*
:RestImportCurl
		Insert a curl command as an .http request. The clipboard is
		used first; when it holds no curl command you are prompted.
		Fills an empty buffer, otherwise appends after the last line.

							*:RestCookiesClear*
:RestCookiesClear
		Delete the cookie jar (session or configured path). See
		|rest.nvim-cookies|.

								*:RestEnv*
:RestEnv [name]
		Show or switch the active environment from `rest-env.json`.
		Without arguments, opens a picker over the environments
		(plus a "(none)" entry that disables environments for the
		session). With `name`, switches directly. See
		|rest.nvim-environments|.

3. CONFIGURATION					*rest.nvim-configuration*

Call the setup function once (values shown are the defaults): >lua

  require("rest").setup({
    base_url = nil,
    timeout_s = 30,
    follow_redirects = false,
    verify_tls = true,
    cookies = { enabled = false, path = nil },
    jq_path = nil,
    ui = { split = "vertical" },
    list = { picker = "auto", dirs = { "." } },
  })
<
base_url		Prepended to relative request URLs. A relative URL
			without base_url is an error.
timeout_s		Request timeout in seconds.
follow_redirects	Follow HTTP redirects when true.
verify_tls		Verify TLS certificates when true.
cookies.enabled		Enable the shared cookie jar |rest.nvim-cookies|.
cookies.path		Persistent jar path; a session-only temporary file
			when unset.
jq_path			Path to the jq binary; auto-detected when nil.
ui.split		"vertical", "horizontal" or "none" for the response
			window.
list.picker		"auto", "snacks", "telescope", "fzf" or "select".
list.dirs		Directories searched by |:RestList|.

4. ENVIRONMENTS					*rest.nvim-environments*

Request variables can come from a `rest-env.json` file, searched upward
from the working directory: >

  {
    "default": "dev",
    "environments": {
      "dev": { "host": "http://localhost:8000", "token": "dev-secret" },
      "prod": { "host": "https://api.example.com", "token": "prod-secret" }
    }
  }
<
Requests resolve `$host`, `$token` and so on from the active
environment: the file's `default` unless |:RestEnv| switches it. Values
may be strings, numbers or booleans.

Precedence: file-level `@definitions` and response references win over
environment variables of the same name.

The file is re-read on every request, so edits apply immediately. A
broken file is reported and skipped; a missing file is not an error.

5. PLUGIN GLOBALS					*rest.nvim-globals*

The `$_` prefix is reserved for plugin globals. Defining a variable
whose name starts with `_` (a file-level `@definition` or an entry in
|rest.nvim-environments|) shows a warning and stops the request.

$_now		Moment the request is resolved, as a local ISO 8601
		timestamp (`2026-10-15T14:30:05`). All $_now references
		in one request see the same instant.

		  `$_now`	`2026-10-15T14:30:05`
		  `$_now.year`	`2026`
		  `$_now.month`	`10` (zero-padded)
		  `$_now.day`	`15` (zero-padded)
		  `$_now.hour`	`14` (zero-padded)
		  `$_now.minute` `30` (zero-padded)
		  `$_now.second` `05` (zero-padded)

		Fields shift with `.add(n)` / `.sub(n)` (integer n); the
		result is the full timestamp after calendar
		normalization, so it is always a valid time: >
  POST https://api.example.com/sessions
  Content-Type: application/json

  {"expiresAt": "$_now.hour.add(2)", "validUntil": "$_now.day.add(7)"}
<
		At 23:30, `$_now.hour.add(4)` rolls into the next day at
		03:30; on Jan 31, `$_now.month.add(1)` clamps to Feb 28
		(29 in a leap year).

		The same shifts exist as methods directly on $_now,
		chainable in written order. Each link applies to the
		result of the previous one, and a chain may end with a
		field access: >
  POST https://api.example.com/sessions
  Content-Type: application/json

  {"expiresAt": "$_now.addHours(4).addMinutes(2)",
   "remindOn": "$_now.addDays(7).day"}
<
		  addHours(n) / subHours(n)	shift hours
		  addMinutes(n) / subMinutes(n)	shift minutes
		  addSeconds(n) / subSeconds(n)	shift seconds
		  addDays(n) / subDays(n)	shift days
		  addMonths(n) / subMonths(n)	shift months
		  addYears(n) / subYears(n)	shift years

		Chains are order-sensitive: from Jan 31,
		`$_now.addMonths(1).addMonths(1)` lands on Mar 28, while
		`$_now.addMonths(2)` lands on Mar 31. Text after a chain
		that is not part of it stays literal, so
		`$_now.addHours(1).json` keeps the `.json` suffix.

		Definition values are references too (derived variables):
		other definitions, environment values, previous responses
		and $_ globals are all legal inside a `@name = value`, and
		they resolve when the request runs, so every $_now in one
		request (including derived ones) is the same instant: >
  @host = https://api.example.com
  @utctime = $_now.hour.add(4)
  @path = $host/time

  GET $path
  X-Utc-Time: $utctime
<
		Definitions may reference each other in any order; errors
		inside a value are reported as `definition '<name>':
		<error>`, and one that ends up referencing itself (directly
		or through others) is reported as `circular definition:
		<path>`.

6. COOKIES						*rest.nvim-cookies*

With `cookies.enabled`, every request passes a Netscape cookie jar to
curl (`-b`/`-c`), so Set-Cookie values from a login response flow into
later requests. By default the jar is a session-only temporary file;
set `cookies.path` to persist it across Neovim sessions.

|:RestCookiesClear| deletes the jar (session or configured path).

7. HIGHLIGHTING					*rest.nvim-highlighting*

The response UI defines these highlight groups with `default = true`,
so your colorscheme can override them (for example from its
`on_highlights`):

  RestStatusCodeSuccess		2xx
  RestStatusCodeRedirect	3xx
  RestStatusCodeError		4xx
  RestStatusCodeInformation	informational
  RestStatusCodeServerError	5xx
  RestHeadingsAttributes	header names
  RestHeadingsValues		header values
  RestMethod, RestMethodGet, RestMethodPost, RestMethodPut,
  RestMethodPatch, RestMethodDelete, RestMethodHead,
  RestMethodOptions, RestMethodTrace, RestMethodConnect
				request methods in the picker
  RestList			picker rows
